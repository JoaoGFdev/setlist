# Unofficial YouTube discovery for Setlist

Researched 2026-11-05. Primary-source review only; no library installation, live searches, authentication trials, Workers execution, or throughput tests were performed. Target: 1,000 Spotify tracks transferred to YouTube per day across users.

## Findings

**YouTube.js (`youtubei.js`) is the better candidate for an experimental search adapter in this TypeScript app. Neither library establishes a reliable, free 1,000-track/day transfer service.** Keep official authenticated writes and pursue quota approval for the production path.

| Question | YouTube.js / `youtubei.js` | Python `ytmusicapi` |
| --- | --- | --- |
| Search without user login? | Yes at the library/source level: `Innertube.create()` accepts no credentials, and `search()` calls the search endpoint without a login guard. This does not establish availability from Cloudflare IPs. [Getting started](https://ytjs.dev/guide/getting-started), [search source](https://raw.githubusercontent.com/LuanRT/YouTube.js/main/src/Innertube.ts). | Explicitly documented: `YTMusic()` supports unauthenticated searching and public playlist retrieval. [Usage source](https://github.com/sigma67/ytmusicapi/blob/main/docs/source/usage.rst). |
| Batch playlist writes? | `create(title, video_ids)` and `addVideos(playlist_id, video_ids)` accept arrays. Source checks login and maps IDs into one playlist-edit action list, rather than making one official insert per ID. [API](https://ytjs.dev/api/youtubei.js/namespaces/Managers/classes/PlaylistManager), [implementation](https://raw.githubusercontent.com/LuanRT/YouTube.js/main/src/core/managers/PlaylistManager.ts). | `create_playlist(..., video_ids=...)` and `add_playlist_items(..., videoIds=...)` accept lists. Duplicate handling defaults to returning an error without adding items; callers must reconcile retries. [Playlist reference](https://ytmusicapi.readthedocs.io/en/stable/reference/playlists.html). |
| Write authentication? | Cookies are recommended for web clients. OAuth now works only with the TV InnerTube client; the docs do not establish TV support for every playlist operation. [Authentication](https://ytjs.dev/guide/authentication). | Documented OAuth setup requires a Google client of type **TVs and Limited Input devices**, device authorization, and OAuth credentials supplied to the library. [OAuth setup](https://ytmusicapi.readthedocs.io/en/stable/setup/oauth.html). |
| Workers fit? | Promising, not verified: upstream lists Node.js, Deno and browsers, with `fetch`, `EventTarget` and `CustomEvent` requirements. Search-only initialization can disable player retrieval with `retrieve_player: false`. Workers is not explicitly certified by that guide. [Runtime requirements](https://ytjs.dev/guide/getting-started). | Not a direct dependency in the existing TypeScript Worker. Would require a Python service/Worker boundary or a port. Python Workers exist and support pure Python/Pyodide packages, but this does not certify this library's HTTP stack. [Cloudflare Python packages](https://developers.cloudflare.com/workers/languages/python/packages/). |

Array parameters establish batching capability, **not** a tested maximum batch size, atomicity guarantee, or permission to send all 1,000 tracks in one request. Both libraries need a runtime trial before committing to chunk sizes or retry semantics.

## Existing Clerk authorization is not proven reusable

Setlist's [Clerk token adapter](../../src/server/clerk-accounts.ts) retrieves `oauth_google` provider access tokens and checks YouTube scopes; [scope configuration](../../shared/provider-scopes.ts) requests `youtube.force-ssl`. The [provider implementation](../../src/server/providers.ts) targets the official YouTube Data API and also defines Google's web authorization endpoint.

That is evidence for the existing official API integration, not for InnerTube compatibility. A Google OAuth access token is not a YouTube browser cookie. YouTube.js documents cookie authentication for web clients and TV-only OAuth; ytmusicapi documents its own TV/device flow and client credentials. Neither cited authentication guide documents accepting an arbitrary Clerk-managed web OAuth token as a drop-in replacement. Treat reuse as **unverified and unsuitable as an implementation assumption**, not as universally impossible. Unauthenticated discovery needs no Clerk token; unofficial writes would require separately validated authorization and potentially a different user connection flow. [YouTube.js authentication](https://ytjs.dev/guide/authentication), [ytmusicapi OAuth](https://ytmusicapi.readthedocs.io/en/stable/setup/oauth.html).

## Capacity and quota

- **Unofficial limits are unknown.** ytmusicapi explicitly says rate limits exist but publishes no numeric safe allowance. No numeric YouTube.js throughput commitment was found in the reviewed guides. Neither establishes 1,000 searches/day or 1,000 writes/day from shared Workers egress. Library availability is not a service allowance or SLA. [ytmusicapi FAQ](https://ytmusicapi.readthedocs.io/en/stable/faq.html).
- **Search replacement alone does not solve writes.** Official `playlistItems.insert` still costs **50 general-quota units per video**. Thus 1,000 inserts require **50,000 units/day**, plus 50 per playlist creation, reads and retries. The default general allowance is 10,000/day: at most 200 inserts if nothing else consumes it, fewer in a real transfer. Current docs give search a separate default bucket of 100 calls/day; do not use the historical 100-general-units-per-search calculation. [Google quota calculator](https://developers.google.com/youtube/data/determine_quota_cost).
- **Official quota increases require an audit/extension request.** Google specifies compliance review and the Audit and Quota Extension Form, not purchasing extra calls through pay-as-you-go billing. Approval and the resulting allocation are not guaranteed. [Google quota and compliance audits](https://developers.google.com/youtube/data/guides/quota_and_compliance_audits).

## Recommendation and validation gates

1. Prefer official discovery and writes with approved quota for the production target. Request sufficient search allocation and at least 50,000 general units/day plus operational headroom; cache confirmed Spotify-to-YouTube matches to reduce repeated searches.
2. If exploring free unofficial discovery, prototype **YouTube.js search only** behind the provider boundary. Keep existing Clerk-backed official writes. This is an engineering experiment, not a complete quota solution or a finding that the approach is approved by YouTube.
3. Verify the selected package version bundles and executes in Setlist's actual Workers configuration. Check session initialization, fetch behavior, dependencies, cache storage, CPU/memory and errors from deployed egress. Cloudflare supplies only a subset of Node APIs; some importable shims throw when called, so a successful build is insufficient. [Workers Node compatibility](https://developers.cloudflare.com/workers/runtime-apis/nodejs/).
4. Measure matching accuracy, latency, request amplification, throttling and failures on representative transfers before claiming 1,000/day. Use bounded concurrency, backoff and resumable jobs; do not interpret an unknown rate limit as unlimited access. If unofficial writes are later considered, separately test authorization, account/channel selection, batch size, ordering, duplicates and partial-failure recovery.

The runtime and capacity recommendations above are inferences from the documented interfaces and Setlist's architecture, not measured results. Python ytmusicapi remains a useful comparison or separate-service option, but adds a runtime boundary without resolving the authentication or throughput uncertainties.
